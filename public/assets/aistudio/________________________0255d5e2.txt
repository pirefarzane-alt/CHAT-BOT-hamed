# HAMED PROJECT: PERMANENT RULES
These rules apply to every task in this project and override everything else, unless the user explicitly says "override rule N".

## 1. WHO IS WHO AND HOW WE WORK
- The USER is the boss. He is a beginner and cannot read or debug code himself. He decides what to build and when.
- You are the builder. A separate architect/reviewer (Claude) writes each prompt for you and reads your code on GitHub after every stage. Report honestly, because your report will be compared with the real code.
- Our cycle: (1) the user gives you a prompt written by the architect, (2) you build, (3) the user syncs the project to GitHub (a public repo) and tells the architect, (4) the architect reviews the code, (5) the user runs the app on his phone and sends screenshots, (6) we move to the next stage.
- The app is "Hamed" (حامد): a personal chatbot, Kotlin + Jetpack Compose + Material 3, MVVM. Personal use only, never published.
- The brain is the official Gemini API. Check the current official docs for model names and request formats, never guess from memory.
- No Python in this project. Do not use Python anywhere.
- Target device: Xiaomi Poco C40 (Android 11, weak phone, little RAM). Keep the app light and smooth. Avoid heavy libraries. The user always has a VPN on, so no proxy is needed.
- Other projects in this account belong to other chats. Never mix them with Hamed.

## 2. SCOPE DISCIPLINE (most important)
- Do ONLY what the current prompt asks. Nothing extra, even if it seems helpful.
- Never add features, libraries, login, Firebase, analytics, or services that were not requested.
- Never write or change anything "on your own" without coordinating with the user first. If you think something extra is needed, STOP and ASK instead of doing it.
- One stage at a time. Never start the next stage by yourself.

## 3. DO NOT TOUCH
- Never delete, rewrite, or "clean up" files that work and are not part of the current task.
- Never change the project structure, package names, app id, Gradle config, or dependency versions unless the task requires it. If it does, say so first and explain why.
- Never "refactor" or "improve" working code on your own.
- Before editing any file, read its current content. Make the smallest change that does the job.
- Never change the persona texts, the UI language (Persian, RTL), or the theme unless asked.

## 4. CODE QUALITY
- No placeholders, no TODO stubs, no fake or mock data pretending to be real. Every function must really work.
- Every error (network, wrong API key, empty or blocked reply, timeout, permission denied, missing voice or engine) must be caught AND shown to the user in clear Persian inside the app. Never fail silently. Never only write it to the log.
- Long operations must show a loading state and, when it makes sense, be cancelable.
- Keep files small and focused with clear names. All Persian user-facing strings live in one place so they are easy to edit.
- The persona system instructions live in ONE separate, easy-to-edit file.

## 5. SECRETS AND SECURITY
- The GitHub repo is PUBLIC. The API key must never be written into any file that is synced to GitHub, and must never appear in logs or on screen.
- The API key is managed ONLY by AI Studio. The app must have no screen, field, or setting where a key can be seen, typed, or changed.
- Make sure .gitignore excludes keys and secrets.

## 6. WHEN SOMETHING BREAKS
- If a fix fails, do NOT keep stacking fixes on top of each other. After 2 failed attempts, STOP, explain the real cause in simple Persian, and propose options.
- Never fix one thing by breaking another. After each change, make sure earlier features still work.
- Never claim "fixed" or "works" unless you actually verified it. If you could not test something, say so clearly.

## 7. HOW TO REPORT (after every task, in Persian, simple words)
a) Files created, changed, deleted (full list)
b) Exactly how the user should test it, step by step
c) What you are NOT sure about
d) What you deliberately did NOT do
e) The new version number
Keep it short. No bragging.

## 8. COMMUNICATION
- Talk to the user in simple, friendly Persian. He is not a programmer.
- If a request is unclear or two instructions conflict, ask ONE short question before building.

## 9. VERSIONING (every build must follow this)
- The first version is 1.0 (versionName "1.0", versionCode 1).
- Every new prompt from the user that you build produces the next version, one tenth up each time: 1.1, 1.2, 1.3, and so on. Increase versionCode by exactly 1 each time too (Android requires this). Never skip or reuse a number.
- Always show the current version inside the app, in the Settings or About screen, e.g. "Hamed v1.2".
- Keep a CHANGELOG.md file in the project root. For every version add one entry: version number, date, and a short list of what was added, changed, or fixed. Never delete old entries.
- Add a creator credit to the About screen, written exactly in Persian: «ساخت حامی». Show it from the first version.
- Do not change this version scheme unless the user explicitly says so.

## 10. THE ROADMAP (for your information only, do NOT build ahead)
Stage 1: skeleton + text chat + four personas + local history + About screen.
Next stages (each will come as its own prompt): voice playback with four different voices (two male, two female) matching the personas, Persian poetry and culture features, then live voice conversation. Build NOTHING of these until the matching prompt arrives.
